# Сети и балансы: как это работает

Документ описывает путь от запуска бэкенда до цифры баланса на экране: какие
вызовы происходят, в каком порядке, что кэшируется и где всё ломается.
Написан по итогам разбора бага «RPC недоступен, ни одна сеть не вернула
баланс».

Два факта из status-go задают почти всё поведение ниже, поэтому начинаем с них.

1. **RPC-клиент кэшируется навсегда.** `internal/rpc/client.go:200`
   (`getClientUsingCache`) держит `rpcClients[chainID]` и не сбрасывает его при
   изменении настроек сети. Клиент собирается из провайдеров, которые были в
   БД на момент первого обращения, и живёт до `StatusNode.Stop()`.
2. **`wallet_fetchOrGetCachedWalletBalances` — чистое чтение кэша.** Параметр
   `forceRefresh` в `pkg/services/wallet/api.go` игнорируется. Кэш наполняет
   фоновый `MultistandardBalanceController`, а не наш запрос.

Отсюда правило: **провайдеров надо прописать до того, как status-go впервые
обратится к сети**, и **балансы надо перечитывать самим по таймеру**.

## 2. Порядок запуска

Порядок — не стилистика, а требование из факта №1. Нарушение любой пары
соседних шагов даёт ровно тот баг, который разбирался.

```
start_backend (Tauri)
   ↓
initializeApplication             — открывает БД, читает аккаунты
   ↓
reconnectWs                       — WS /signals
   ↓
configureWalletRpc                — форвардер + провайдеры (см. §3)
   ↓
loginAccount → node.login
   ↓
configureWalletRpc                — повторно: сети уже зарегистрированы
   ↓
wakuext_startMessenger            — только теперь, messenger создаёт RPC-клиенты
   ↓
wallet_startWallet                — один раз за сессию
   ↓
опрос балансов каждые 3 с
```

Почему `startMessenger` стоит **после** `configureWalletRpc`: messenger при
старте обращается к сети (curated communities, метаданные токенов). Первое
обращение создаёт RPC-клиент — и если в этот момент в БД лежат встроенные
провайдеры, клиент навсегда соберётся из них.

Почему `configureWalletRpc` вызывается дважды: до логина сервис `networks_*`
ещё не зарегистрирован в RPC-сервере (`initServices` идёт после старта ноды),
поэтому первый вызов только поднимает форвардер, а провайдеров прописывает
второй.

Форвардер поднимается **первым** и независимо от status-go. Это команда
Tauri, она доступна всегда; провайдер с прошлого запуска уже лежит в БД и
может быть вызван немедленно — к этому моменту прокси обязан принимать.

## 3. Локальный форвардер

### Зачем

`traffic.PrivateTransport` в status-go — клон `http.DefaultTransport` с
пулом keep-alive соединений. В этом канале соединения тихо умирают: сокет
остаётся `ESTAB`, пакеты уходят, ответов нет, ретрансмиты копятся до
`tcp_retries2`. Запрос висит 20 с (таймаут circuit breaker) и падает.
`curl`, который открывает свежее соединение на каждый запрос, в тех же
условиях работает.

Поэтому провайдер указывает не на сеть, а на локальный форвардер, который
открывает свежее соединение на каждый запрос.

### Устройство

```
status-go ──HTTP──> 127.0.0.1:43057/<chainId> ──reqwest──> upstream
```

- **Порт постоянный: 43057** (`PREFERRED_PORT`). Обязательно: URL провайдера
  сохраняется в БД status-go и переживает перезапуск приложения. Со случайным
  портом на следующем старте провайдер указывал бы в никуда. Если порт занят
  (жив старый экземпляр) — берётся случайный, и провайдеры перезаписываются.
- **Пул отключён:** `reqwest::Client::builder().pool_max_idle_per_host(0)`.
  Каждое соединение живёт один запрос. В этом и смысл.
- **Маршрутизация по пути:** `/<chainId>`. Таблица `chainId → URL` задаётся
  командой `set_rpc_upstreams`.
- **Ответы:** `200` с телом upstream, `503` если для сети нет upstream,
  `502` с JSON-RPC-ошибкой если upstream не ответил. Именно JSON-RPC-ошибка,
  а не молчаливый обрыв: иначе `ethclient` видит EOF и повторяет запрос,
  хотя причина уже известна.
- **Лимиты:** заголовки 64 КБ, тело 32 МБ.
- **`Connection: close`** в каждом ответе — соединение не переиспользуется
  ни в одну сторону.

Форвардер не смотрит на содержимое запроса: он передаёт байты как есть.
Авторизация (API-ключ) живёт в URL upstream, поэтому ключ не покидает
машину — наружу уходит только запрос к самому провайдеру.

### Команды Tauri

| Команда | Назначение |
|---|---|
| `start_rpc_proxy` | Поднять форвардер, вернуть порт |
| `set_rpc_upstreams` | Задать `{chainId: url}`, можно менять на ходу |
| `stop_rpc_proxy` | Остановить (вызывается при выходе) |

## 4. Выбор провайдера

```ts
const PUBLIC_RPC = { 1: 'https://ethereum-rpc.publicnode.com', 10: '…optimism…', … };
const ALCHEMY_HOSTS = { 1: 'eth-mainnet', 10: 'opt-mainnet', … };
```

Основной — **publicnode** для семи сетей (Ethereum, Optimism, BSC, Base,
Arbitrum, Sepolia, BSC-testnet). Alchemy из `VITE_ALCHEMY_KEY` — запасной,
только для сетей из `ALCHEMY_HOSTS`.

Почему так: Alchemy 403-ит на L2, не подключённых к тарифу (`opt-mainnet`,
`base-mainnet`, `arb-mainnet` возвращают `403`), а на этой машине он ещё и
молча умирает — соединение `ESTAB`, ответов нет. publicnode отвечает за
0.12–0.18 с на те же 300 вызовов multicall.

Провайдер пишется только активным сетям:

```ts
if (!chainId || !chain.enabled || !chain.isActive) continue;
```

**Имена полей — `enabled` и `isActive`**, как в `params.Network`. Поле
`active` не существует; фильтр по нему молча отбирает 0 сетей, и провайдеров
не появляется вовсе. Эта ошибка уже стоила одного полного круга отладки.

Запись провайдера:

```ts
await setChainUserRpcProvider(port, chainId, 'stauri-rpc', `http://127.0.0.1:${proxyPort}/${chainId}`);
```

Имя `stauri-rpc` используется и для проверки «уже добавлен»: перед записью
сверяется не только имя, но и URL — провайдер мог остаться от прошлой
конфигурации с мёртвым адресом.

Запись идёт через `networks_setChainUserRpcProviders`. Валидация status-go
(`pkg/services/networks/validate.go`) проверяет только auth-поля, `http://` и
loopback не запрещает. `InitEmbeddedNetworks` при логине сохраняет
user-провайдеров (`network.go:168`), не затирает. `Find()` читает БД на
каждый вызов, так что запись до первого `EthClient` подхватывается.

## 5. Адреса кошелька

Здесь был основной баг. Адресов в профиле несколько, и они не равнозначны:

| Поле | Пример | Кошелёк? |
|---|---|---|
| `wallet-root-address` (из `settings_getSettings`) | `0xf538b590…` | **нет** |
| `address` (корневой аккаунт) | `0x4c9ce7e3…` | нет |
| `dapps-address` | `0x8d5a8c80…` | нет |
| аккаунт с `chat = false` | `0x8d5a8c80…` | **да** |

Контроллер балансов считает для адресов из `keypairs_accounts` с фильтром
`chat = 0 AND removed = 0` (`internal/db/multiaccounts/accounts/database.go`,
`GetWalletAddresses`). В профиле это обычные аккаунты — те, что видны в UI
как «Account 1».

Запрос по `wallet-root-address` возвращает **пустой результат**: ключа такого
адреса в кэше просто нет. Пустой ответ легко принять за «все балансы с
ошибкой» и уйти чинить провайдеров, которые ни при чём.

Поэтому адреса берутся из `accounts_getAccounts`, с отбрасыванием `chat`:

```ts
const accounts = await getAccounts(port);
const addresses = accounts.filter(a => a && a.address && !a.chat).map(a => String(a.address));
```

и **все** передаются в запрос балансов: ответ содержит запись на каждый
запрошенный адрес, токены собираются по всем.

## 6. Балансы

### Формат ответа

```jsonc
{
  "0x8d5a…": [
    { "tokenAddress": "0x0000…", "tokenChainId": 1, "rawBalance": "1000000000000000000", "hasError": false }
  ]
}
```

`StorageToken` — **не содержит `symbol` и `decimals`**. Без них баланс не
подписать и не перевести в человеческие единицы. Метаданные даёт отдельный
`wallet_getTokensForActiveNetworksMode`, сопоставление по паре
`(chainId, tokenAddress)`:

```ts
function tokenKey(chainId: number, address: string) { return `${chainId}:${address.toLowerCase()}`; }
```

`rawBalance` — минимальные единицы (wei). `formatBalance` в UI ждёт именно их.

### `hasError`

Означает «RPC не ответил», а не «баланс ноль». Три состояния различаются:

| Ситуация | Что показываем |
|---|---|
| Токенов 0 | «Каталог токенов пуст» — чинить сети/токены, не провайдеров |
| Все токены `hasError` | «RPC недоступен» — чинить провайдеров |
| Часть `hasError` | Метка на конкретных токенах |
| Все без ошибок | Ничего лишнего |

Нулевые балансы **не отбрасываются**: иначе недоступность сети выглядит как
пустой кошелёк, а реально нулевой счёт — как ошибка. Сортировка: сначала
ненулевые, дальше по символу.

### Опрос

`wallet_fetchOrGetCachedWalletBalances` читает кэш, `forceRefresh`
игнорируется. Кэш наполняет фоновый контроллер, поэтому UI перечитывает его
каждые 3 с (`startWalletPolling`). `wallet_startWallet` вызывается **один раз
за сессию** (`walletState.loaded`), повторные вызовы бессмысленны.

`rpcError` **не сбрасывается в начале опроса** — только перезаписывается
ответом. Иначе каждый тик на мгновение убирает плашку, и UI мигает между
ошибкой и списком нулей.

### Когда каталог токенов пуст

`wallet_getAllTokens` = 0, `wallet_getAllTokenLists` = только «Community
tokens», `wallet_getBlockchainHealthStatus` → `statusPerChain: {}` (запросов
к сети не было). Значит, каталог не наполнился, и контроллеру нечего
запрашивать. Это **не** ошибка RPC; симптом — 21 токен с `hasError` при
наличии невыполненных сетевых запросов.

## 7. Как отлаживать

Сначала посмотреть каталог. Это отвечает на вопрос «а запросы вообще были?»:

```bash
P=$(ps -o args= -p $(pgrep -f 'status-backend -address') | grep -oE '127\.0\.0\.1:[0-9]+' | cut -d: -f2)
call() { curl -s --noproxy '*' -X POST "http://127.0.0.1:$P/statusgo/CallRPC" \
  -H 'Content-Type: application/json' -d "$1"; }

call '{"jsonrpc":"2.0","id":1,"method":"wallet_getAllTokens","params":[]}' | head -c 200
```

Признаки, по которым различаются причины:

| Наблюдение | Причина |
|---|---|
| `wallet_getAllTokens` = 0 | Каталог токенов не наполнен — провайдеры ни при чём |
| Каталог полный, `statusPerChain: {}` | К сети не ходили вообще |
| В логе `dial tcp: lookup …rpc.grove.city: no such host` | Используются встроенные провайдеры, наш не прописан |
| `stauri-rpc` есть, `enabled=True`, а соединений к 43057 нет | RPC-клиент собран раньше записи провайдеров (см. факт №1) |
| Все токены `hasError`, соединения к 43057 есть | Проблема на стороне upstream, а не status-go |

Счётчик соединений к форвардеру:

```bash
ss -tnp | grep "pid=$(pgrep -f 'status-backend -address')" | grep -c :43057
```

Проверка самого форвардера, в обход status-go:

```bash
curl -s --noproxy '*' -X POST http://127.0.0.1:43057/1 \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}'
```

Здоровье провайдеров по сетям:

```bash
call '{"jsonrpc":"2.0","id":1,"method":"wallet_getBlockchainHealthStatus","params":[]}'
```

### Ловушки отладки

- **Профильный лог перестаёт писаться.** `…/mainnet/status.log/<key>.log`
  может «замереть»: неизменный размер файла не значит «ничего не происходит».
  Опираться на отсутствие строк в нём нельзя. Пред-логин лог — отдельный
  файл, `~/.config/Status/logs/pre_login.log`.
- **Закэшированные ответы.** `wallet_fetchOrGetCachedWalletBalances`
  возвращает одно и то же, пока контроллер не перезапишет кэш. Сравнивать
  ответы до и после «исправления» бессмысленно.
- **Устаревший процесс.** Проверять время старта процесса против времени
  правки файлов: правка в сторе не действует на уже запущенное приложение.
- **`wallet-root-address` ≠ адрес счёта.** См. §5.
- **Пустой результат ≠ ошибка.** Пустой ответ по чужому адресу выглядит как
  провал всех сетей.

## 8. Сводка инвариантов

1. Форвардер слушает постоянный порт `43057`; провайдеры указывают только на
   `http://127.0.0.1:43057/<chainId>`.
2. Форвардер поднимается раньше всех обращений к сети и не зависит от
   готовности status-go.
3. Провайдеры прописываются **до** `wakuext_startMessenger` — иначе
   RPC-клиент навсегда соберётся из встроенных провайдеров.
4. Фильтр сетей — `enabled && isActive`.
5. Адреса для балансов — аккаунты с `chat = false`, не
   `wallet-root-address`.
6. `symbol` и `decimals` берутся из `wallet_getTokensForActiveNetworksMode`
   и сопоставляются по `(chainId, tokenAddress)`.
7. Балансы перечитываются по таймеру; `forceRefresh` не работает.
8. Нули показываются, `hasError` не скрывается, три состояния
   (пустой каталог / RPC недоступен / всё нормально) различаются в UI.
