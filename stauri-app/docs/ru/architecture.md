# Архитектура Stauri

Документ описывает, как устроен Stauri «в целом»: из каких слоёв он состоит,
как они общаются и почему границы проведены именно так. Он дополняет
`networks_and_balances.md` (там — конкретный путь баланса на экран) и
`status_outdated_architecture.md` (там — почему `status-go` устроен сложно).

## 1. Главное решение: сайдкар вместо библиотеки

Stauri не линкует `status-go` как библиотеку. Он запускает `status-backend`
как **отдельный процесс** (sidecar) и общается с ним по двум каналам:

- **HTTP** (`http://127.0.0.1:<port>/statusgo/CallRPC`) — запросы;
- **WebSocket** (`ws://127.0.0.1:<port>/signals`) — асинхронные сигналы.

Причины ровно две:

1. **Жизненный цикл.** Падение или перезапуск `status-go` не должен утаскивать
   UI. Процесс можно убить и поднять заново, не трогая окно приложения.
2. **Версионирование.** Бинарник `status-go` собирается отдельно (Nix/Go),
   а фронтенд — на Svelte. Их можно обновлять независимо, если контракт
   JSON-RPC не меняется.

Плата за это — управление процессом: `start_backend` / `stop_backend`,
PID-файл, убийство «зомби» при старте. Всё это живёт в `src-tauri/src/lib.rs`.

## 2. Слои

┌──────────────────────────────────────────────────────────┐
│ UI (Svelte 5) │
│ routes/+page.svelte, sections/, components/ui/ │
├──────────────────────────────────────────────────────────┤
│ Сторы (Svelte 5 runes, .svelte.ts) │
│ statusStore, connectionStore, walletStore, chatsStore │
├──────────────────────────────────────────────────────────┤
│ Обёртки API (TypeScript) │
│ api.ts (вызовы), http.ts (транспорт), types.ts │
├──────────────────────────────────────────────────────────┤
│ Tauri (Rust) │
│ lib.rs: start_backend, RPC-форвардер, dApp-окна │
│ rpc_proxy.rs: локальный HTTP-форвардер │
├──────────────────────────────────────────────────────────┤
│ status-backend (сайдкар) │
│ HTTP RPC + WS сигналы │
└──────────────────────────────────────────────────────────┘
text


Границы проведены по **времени жизни** и **частоте изменения**:

- **UI** меняется постоянно, зависит только от сторов.
- **Сторы** — единственное место с изменяемым состоянием; UI их только
  читает и вызывает действия.
- **`api.ts`** — чистая обёртка: знает про методы и параметры, не знает про
  состояние.
- **`http.ts`** — единственное место, где живёт транспорт, логирование и
  разбор ошибок JSON-RPC.
- **Tauri** — процессы, окна, локальные сокеты. Там, где нужен Rust
  (`reqwest`, `tokio`, `std::process`).
- **`status-backend`** — «чёрный ящик» со своим состоянием и кэшами.

Ничто выше Tauri не знает, что внутри Rust. Ничто выше `api.ts` не знает,
что внутри HTTP. Это позволяет менять транспорт (например, на Unix-socket),
не трогая сторы.

## 3. Поток данных

### 3.1. Запрос-ответ (HTTP)

UI → store.method() → api.ts → http.ts → tauriFetch
→ 127.0.0.1:<port>/statusgo/CallRPC
→ status-backend → JSON-RPC → ответ
← http.ts разбирает error, возвращает data
← store обновляет $state
← UI перерисовывается
text


`http.ts` (`statusFetch`) — единственная точка, где:
- маскируются секреты в логах (сейчас — только `password`, см. TODO);
- пустой ответ превращается в `{}`;
- ошибки JSON-RPC (`error.message`) превращаются в `Error` с текстом.

Это значит: сторы **не** разбирают HTTP-статусы и не знают про JSON-RPC.
Если завтра транспорт сменится, правка будет в одном файле.

### 3.2. Сигналы (WebSocket)

status-backend → WS /signals → connectionStore.reconnectWs
→ statusStore.processSignal(rawJson)
→ обновление $state или вызов функции
text


`processSignal` — единственный потребитель сигналов. Сейчас он знает три
типа: `node.login`, `node.stopped`, `messages.new`. Всё остальное молча
игнорируется (кроме пуша в `statusState.events` для отладки).

**Важно:** `processSignal` синхронный и не делает сетевых вызовов. Если
сигнал требует асинхронной реакции (например, `wallet.router.sign-transactions`
в будущем), её нужно запускать отдельно, не блокируя разбор следующего
сигнала.

### 3.3. Состояние

Всё состояние — в `$state`-объектах сторов:

| Стор | Что хранит |
|---|---|
| `statusState` | Соединение, логин, аккаунты, сеть, сигналы |
| `connectionState` | Процесс соединения (`isConnecting`), выбранная сеть |
| `walletState` | Адрес, балансы, метаданные, `rpcError` |
| `chatsState` | Чаты, контакты, выбранный чат |
| `contactsState` | Контакты, выбранный контакт |

Правила:
- **Никакого состояния в компонентах**, кроме локального UI (открыта ли
  модалка, текст в поле).
- **Никаких прямых вызовов `api.ts` из UI** — только через действия сторов.
- **Стор не знает про UI.** Он возвращает данные и ошибки, UI решает, как
  их показать.

## 4. Ключевые подсистемы

### 4.1. Запуск и логин

Порядок — не стилистика, а требование из кэша RPC-клиентов `status-go`
(см. `networks_and_balances.md`, §2). Кратко:

start_backend → initializeApplication → reconnectWs
→ configureWalletRpc (форвардер + провайдеры)
→ loginAccount → node.login
→ configureWalletRpc (повторно)
→ [если wroteProviders] logout → node.stopped → loginAccount
→ startMessenger → wallet_startWallet
→ polling балансов
text


`connectionStore` — единственный, кто знает этот порядок. Ни UI, ни
`walletStore` не вызывают `loginAccount` напрямую.

### 4.2. RPC-форвардер

`src-tauri/src/rpc_proxy.rs` — локальный HTTP-сервер на `127.0.0.1:43057`.
Причина существования — залипание TCP-соединений в пуле `status-go`
(подробно в `networks_and_balances.md`, §3). Форвардер открывает новое
соединение на каждый запрос (`pool_max_idle_per_host(0)`), поэтому ведёт
себя как `curl`, а не как `http.DefaultTransport`.

С точки зрения фронтенда это просто ещё одна команда Tauri
(`start_rpc_proxy` / `set_rpc_upstreams` / `stop_rpc_proxy`). Фронтенд не
знает, что внутри `reqwest`.

### 4.3. Кошелёк

`walletStore` — самый сложный стор, потому что зависит от двух кэшей
`status-go` (RPC-клиенты и кэш балансов) и от метаданных токенов. Ключевые
решения:

- **Адреса** берутся из `accounts_getAccounts` (фильтр `!chat`), а не из
  `wallet-root-address`.
- **Метаданные** (`symbol`, `decimals`) — из
  `wallet_getTokensForActiveNetworksMode`, сопоставление по
  `(chainId, tokenAddress)`.
- **Опрос** — по таймеру (`startWalletPolling`), потому что `forceRefresh`
  игнорируется.
- **Три состояния** различаются в UI: пустой каталог / RPC недоступен /
  всё нормально.

### 4.4. dApp-окна

`open_dapp_window` создаёт отдельное окно Tauri с `WebviewUrl::External`.
Это изоляция: dApp не имеет доступа к `window.__TAURI__` главного окна,
и его падение не утаскивает Stauri.

В будущем — безопасная инъекция `window.ethereum` с гранулированными
разрешениями (см. `README_ru.md`, «Безопасность через изоляцию»).

## 5. Почему именно так (альтернативы)

| Альтернатива | Почему не выбрана |
|---|---|
| Линковать `status-go` как библиотеку | Падение бэкенда = падение UI; версии жёстко связаны |
| Вызывать `status-go` напрямую из JS | Нет `reqwest`/`tokio`, нет управления процессами, нет форвардера |
| Держать всё состояние в одном сторе | Сторы начинают зависеть друг от друга; тесты усложняются |
| Общаться с блокчейном напрямую из UI | Нет keystore, нет подписи, нет мультичейна; `status-go` всё равно нужен для мессенджера |
| Использовать готовый `status-desktop` | Монолит QML; нет модульности, нет dApp-изоляции, нет Svelte |

## 6. Инварианты архитектуры

1. UI не вызывает `api.ts` напрямую — только через сторы.
2. `http.ts` — единственное место с транспортом и разбором ошибок.
3. `processSignal` синхронный; асинхронные реакции запускаются отдельно.
4. `connectionStore` — единственный, кто знает порядок запуска и логина.
5. Секреты (пароли, ключи) не попадают в логи (см. TODO — маскирование
   ключей пока не сделано).
6. dApp-окна изолированы от главного окна.
7. Rust-команды — единственный способ общаться с ОС (процессы, сокеты,
   окна).

## 7. Что меняется при добавлении функции

Типичный путь новой функции (например, Send):

1. **`api.ts`** — обёртка над методом `status-go`.
2. **`newStore.svelte.ts`** — состояние и действия (если нужно).
3. **`processSignal`** — если метод отвечает сигналом, а не результатом.
4. **UI-компонент** — читает стор, вызывает действия.
5. **Тесты** — юнит-тесты стора (моки `api.ts`), при необходимости —
   интеграционный тест на `statusFetch`.

Если шаг 3 нужен, это сигнал, что операция асинхронная и её нельзя
сделать «в лоб» из UI. Пример в будущем — Router (`wallet.router.*`).
