разрыв. Порядок продиктован одним правилом: **до первого реального перевода
всё, что можно проверить бесплатно, проверить в Testnet.**

Связанные документы: `docs/ru/networks_and_balances.md` (как приходят
балансы), `docs/ru/architecture.md` (слои), `docs/PLAN.md` (общие этапы).

## 2. Что нужно решить до кода

### 2.1. QR-код получает сторонний сервис (блокер, чинится сразу)

`WalletReceiveTab.svelte:18` строит картинку через
`https://api.qrserver.com/v1/create-qr-code/?data=<адрес>`. Две проблемы:

* в CSP (`svelte.config.js:23`) этого хоста нет — картинка просто не
  загрузится, то есть сейчас QR на экране отсутствует;
* даже если добавить хост в CSP, каждый показ вкладки «Получить» отдаёт
  адрес кошелька чужому серверу. Адрес не секрет, но связывать его с нашим
  клиентом незачем.

Решение: генерировать QR локально библиотекой на JS (`qrcode`, работает
офлайн). Заодно исчезает сетевая зависимость экрана получения.

### 2.2. Пароль при подписи (решает пользователь)

Отправка в status-go двухшаговая и **требует пароль на каждом переводе**:

```
wallet_buildTransaction(chainID, sendTxArgsJSON)
   → { messageToSign, txArgs }            // hash, который надо подписать
wallet_signMessage(messageToSign, from, password)
   → подпись                             // разблокирует ключ паролем
wallet_sendTransactionWithSignature(chainID, "WalletTransfer", txArgsJSON, sig)
   → txHash
```

(`pkg/services/wallet/api.go:567, 578, 605`; `SignMessage` внутри —
`gethManager.LoadAccount(address, password)`.)

Варианты:

| Вариант | Плюс | Минус |
|---|---|---|
| Спрашивать пароль на каждую отправку | Ключ не живёт в памяти | Утомительно |
| Держать пароль в памяти сессии после первого ввода | Как в мобильном Status | Пароль доступен процессу всё время работы |
| KDF + хранение на диске | Удобно | Это уже полноценный keystore — наша задача, не стоит |

Предлагаю **второй** вариант с явным окном «Подтвердить паролем»: пароль
вводится один раз за сессию, стирается при выходе из аккаунта и при смене
раздела не нужен. Решение за пользователем — это меняет модель угроз.

### 2.3. `wallet_signMessage` — это оракул подписи

`wallet_signMessage` подписывает **любые** 32 байта ключом аккаунта. Пока
бэкенд доступен только через `auth_proxy` с токеном — это приемлемо (см.
`src-tauri/src/auth_proxy.rs`). Но когда появится любой другой доступ к
ноде, это станет дырой: чужой процесс сможет подписать перевод, который
сам же и собрал.

Решение: пока ничего не менять, но **записать это в §13 PLAN.md** как риск,
который надо закрыть до появления внешнего доступа (в терминах Logos —
тем более).

## 3. Поверхность status-go, которую будем использовать

Проверено по локальному checkout `~/ETH/github.status-go`.

| Задача | Метод | Замечание |
|---|---|---|
| Оценка газа и цены | `wallet_getSuggestedFees(chainID)` | `SuggestedFeesGwei` |
| Время подтверждения | `wallet_getTransactionEstimatedTimeV2` | Опционально |
| Собрать перевод | `wallet_buildTransaction` | Возвращает hash для подписи |
| Подписать | `wallet_signMessage` | Нужен пароль (см. §2.2) |
| Отправить | `wallet_sendTransactionWithSignature` | `txType = "WalletTransfer"` |
| Ожидающие транзакции | `wallet_getPendingTransactions` | Для статуса в UI |
| Проверить/разобрать адрес | `wallet_getAddressDetails(chainID, addr)` | Показывает ENS-имя адреса |
| Купить | `wallet_getCryptoOnRamps`, `wallet_getCryptoOnRampURL` | Провайдеры + ссылка с `destAddress` |
| ENS: мои имена | `ens_getEnsUsernames` | namespace `ens` |
| ENS: цена, владелец, срок | `ens_price`, `ens_ownerOf`, `ens_expireAt` | |
| ENS: адрес по имени / имя по адресу | `ens_addressOf`, `ens_getName` | Нужно и в Send, и в профиле |
| ENS: регистрация/снятие | **через Router**, `SendType: ENSRegister/ENSRelease` | Не через `buildTransaction` |

Важно: **регистрация ENS идёт только Router-путём** (`RouteInputParams` с
`sendType`, `username`, `publicKey`; на mainnet оплата в SNT, на testnet —
в STT, см. `requests/router_input_params.go:18-22`). Для обычного перевода
Router не нужен — начинаем с простого пути и не тащим роутер в первый
спринт.

## 4. Порядок работ

### Этап 1. Подготовка (без сети, без денег) — ВЫПОЛНЕНО

1.1. QR локально; убрать `api.qrserver.com` из кода.
`src/lib/components/QrCode.svelte` на библиотеке `qrcode` (devDependency,
код попадает в бандл при сборке).

1.2. Фильтр в списке «Отправить»: сейчас в выпадающий список попадают все
токены, включая нулевые и `hasError`. Оставить только то, с чем реально
можно отправить, остальное — в отдельную группу «недоступно».
`src/lib/utils/tokens.ts`, `groupTokensForSending` + `checkAmountAgainstBalance`.

1.3. Новый слой API: `src/lib/status/wallet.ts` (по образцу
`messaging.ts`) — все `wallet_*` и `ens_*`, которые нам нужны. Сторы не
должны знать про JSON-RPC напрямую; это же упростит замену на Logos.
`api.ts` сохраняет реэкспорт для существующих вызовов.

1.4. `src/lib/utils/amount.ts`: разбор ввода `"0.5"` → минимальные единицы
(`BigInt`, без float) и обратно. `parseFloat` в форме отправки недопустим —
0.1 ETH в float это 0.09999999999999999. Ошибки разбора — коды
(`AmountErrorCode`), текст переводит интерфейс.

Проверка: unit-тесты на `amount.ts` и на фильтр токенов. Пересборка, ручной
просмотр «Получить».

### Этап 2. Testnet как рабочая площадка

2.1. Запуск с `STAURI_NETWORK=sepolia` (или `holesky`). Проверить, что:
* данные пишутся в отдельный каталог (уже есть, `config.data_dir_suffix`);
* баланс приходит (ETH и хотя бы один ERC-20);
* вкладка Assets не показывает ошибок RPC.

2.2. **Проверить, что вообще живёт на testnet:** `wallet_getCryptoOnRamps`
в testnet-режиме может вернуть пустой список, ENS-регистрация на Sepolia
требует контрактов Status. Это надо выяснить здесь, а не на mainnet.

2.3. Подготовить два адреса: свой (в приложении) и адрес-получатель (любой
второй кошелёк/ключ). Краны для Sepolia.

### Этап 3. Send (testnet)

3.1. `stores/sendStore.svelte.ts` — состояние формы и шага подтверждения:
токен → получатель → сумма → оценка комиссии → пароль → отправка.

3.2. Получатель принимает **и `0x…`, и ENS-имя**. Разбор через
`wallet_getAddressDetails`; ошибка ввода показывается до нажатия «Отправить».

3.3. Экран подтверждения показывает **всё, что уйдёт**: сеть, токен, сумма,
комиссия, итог. Никаких «Отправить» без этой строки.

3.4. После отправки: сообщение о pending с хэшем и ссылкой на обозреватель
(`open_external`, уже есть). Баланс сам не обновится — кэш наполняет фон
(status-go игнорирует `forceRefresh`), поэтому обновляем явно и пишем в UI
«обновляется фоном».

3.5. Обработка ошибок: недостаточно средств, неверный адрес, RPC не
ответил, отказ подписи. Каждая — отдельным текстом, а не «Failed».

Проверка: перевод ETH на Sepolia между двумя своими адресами, затем ERC-20.
Смотрим в обозревателе, что транзакция действительна.

### Этап 4. Receive

4.1. Локальный QR, адрес, кнопка копирования (есть).

4.2. Предупреждение: перечислять сеть/токен. Адрес один на все сети
(EVM), и это опасное место для пользователя — «отправь ETH» и «отправь
USDT в сети Optimism» приходят на один и тот же `0x…`.

### Этап 5. Buy (on-ramp)

5.1. `wallet_getCryptoOnRamps` → список провайдеров (id, имя, сборы,
поддерживаемые сети/токены).

5.2. `wallet_getCryptoOnRampURL(providerID, { destAddress, chainID, symbol })`
→ ссылка → `open_external`. Это обычный внешний сайт, платёж идёт у него;
наш код только передаёт адрес.

5.3. Если список пуст (обычно в testnet) — понятное сообщение, а не пустая
вкладка.

Проверка: в testnet — список пуст и это ожидаемо; в mainnet — ссылка
открывается и адрес подставлен.

### Этап 6. ENS

6.1. Чтение (безопасно, в mainnet): `ens_getEnsUsernames` — показывать
своё имя в профиле вместо заглушки; `ens_getName` — показывать имя вместо
адреса в поле получателя.

6.2. `ens_getName`/`ens_addressOf` в Send: обратное преобразование адреса в
имя и наоборот.

6.3. Регистрация имени — отдельным этапом и только через Router. Сначала
посмотреть на testnet, работает ли регистрация вообще; если нет — на
mainnet одним дешёвым именем. Здесь же `ens_price` и `ens_expireAt`, чтобы
человек видел срок.

### Этап 7. Mainnet, реальные деньги

Правила этого этапа — не пожелания, а условие:

1. Сначала **сухой прогон**: всё до шага подписи, включая оценку комиссии,
   затем отмена. Убедиться, что суммы и адреса верные.
2. Первый реальный перевод — минимальный (сумма на уровне «пыль», но
   комиссия при этом ненулевая). Цель — проверить путь, а не сумму.
3. Второй — ERC-20 с ненулевым `decimals ≠ 18` (например, USDC — 6):
   именно тут вылезают ошибки пересчёта, которых не видно на ETH.
4. Отдельный счёт или свежий профиль Stauri. Основной кошелёк не подключаем,
   пока не пройдены пункты 2–3.
5. После каждого шага сверять хэш в обозревателе.

### Этап 8. Документы и тесты

8.1. `docs/ru/wallet.md`: путь перевода по вызовам, как и
`networks_and_balances.md`, плюс раздел «где сломается».
8.2. Unit-тесты: `amount.ts`, `sendStore` (валидация, шаги), выбор
провайдера on-ramp, разбор ошибок status-go.
8.3. Риск из §2.3 — в `docs/PLAN.md`.

## 5. Что НЕ входит в этот этап

* Swap и Bridge — Router, отдельная большая тема.
* История транзакций (`wallet_startActivityFilterSessionV2` + сигналы) —
  нужна, но не блокирует отправку; отдельным этапом.
* Собственные коллекции/NFT.
* Аппаратный кошелёк (keycard).

## 6. Риски

| Риск | Как снимаем |
|---|---|
| Подпись требует пароль на каждое действие | Решение в §2.2; пароль в памяти сессии, стирается при выходе |
| Кэш балансов не обновляется после перевода | Явное обновление + статус pending; не обещать мгновенного баланса |
| float в суммах | `BigInt` в `amount.ts`, запрет `parseFloat` в формах |
| Testnet-возможности отличаются от mainnet | Этап 2.2: выяснить заранее |
| Сеть одна, адрес один (EVM) | Предупреждение на экране получения |
| Ошибки RPC выглядят как пустой кошелёк | Уже частично решено (`rpcError`), довести до Send |
| Замена status-go на Logos | Все вызовы через `status/wallet.ts` — граница одна |

## 7. Готово, когда

* На Sepolia: отправка ETH и ERC-20 между своими адресами, подтверждение
  видно в обозревателе, баланс обновляется.
* QR на экране «Получить» рисуется локально.
* On-ramp отдаёт ссылку с подставленным адресом (mainnet).
* ENS-имя видно в профиле и в поле получателя.
* На mainnet: один минимальный ETH-перевод и один ERC-20-перевод, оба
  сверены в обозревателе.
* Ни в одном логе нет пароля, seed-фразы и приватного ключа.
